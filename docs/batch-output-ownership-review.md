# 2.0.0：批量输出计数与所有权发布复核

本轮确认并修复 DLL 批量操作把调用方输出计数当作内部退休依据的问题。版本固定为 2.0.0，单 DLL/单 SYS、旧 Wintun 接口、v2 数据布局和接口表布局保持不变。

## 已复现的问题

ReleaseBatch 原来把公开 accepted 指针直接传给 recycle producer，并在发布后反复读取它，决定私有 token 循环边界和 Loans 扣减。输入 token 的私有快照已经保护了 token 内容，但没有保护输出计数。

测试把 accepted 放在本次归还的 TX 数据区。实际 core 发布 Producer 后，确定性对端消费归还 token，使用实际 pool 辅助函数回收并重新预留同一槽位，覆盖其数据并发布下一代描述符。这时输出地址已经属于对端，仍有 DLL 代码读取它：

- 改成 0：旧实现返回成功，却没有退休 DLL 私有槽位或减少 Loans，触发 `REUSED_OUTPUT_COUNT_LOST_RETIREMENT`（退出码 51）。
- 改成 UINT32_MAX：旧循环超过真实批次。测试在进入未初始化/越界 token 读取之前截住，触发 `PUBLIC_COUNT_ESCAPED_BATCH_BOUND`（52），不以崩溃代替证明。

错误的输出存储布局不应控制库内存访问。把输出计数放进即将转交的数据，本身也无法保证返回后仍能读取该值；只改成私有计数、最后回写原地址，还会覆盖对端的下一包。因此修复需要同时处理内部控制数据与输出地址的所有权。

## 修复边界与兼容性

ReleaseBatch、CommitBatch 使用私有局部计数完成状态转换和账本更新；ReserveBatch、PollInternal 同样不再把可被输出记录覆盖的计数用于内部控制。计数输出只报告已经确定的结果，不授权退休、决定 token 循环长度或推算内部借用数。

ReleaseBatch/CommitBatch 在 token 校验后检查输出计数与请求中的数据槽位是否重叠；危险布局在发布前返回 PB_INVALID，接受数为零，原有借用不变，可用独立计数重试。检查覆盖整个转交槽位及四字节输出的边界交叉，不能依赖“当前只有一小段报文”来保留已经转交的容量。整个请求都可能被接受，不能把请求后缀当作保证仍会持有的存储。

继续支持计数放在未参与本次转交、仍由调用方持有的其他借用中。输入 token 放在正在归还的 payload 中也继续由原有快照保护。原先从未持有的、已经归还的或并发转交的存储，不能作为本次输出。无效 token/所有者、停止/故障、部分接受和失败时输出清零的原有处理顺序保持现有约定。

未增加分配、句柄、线程、原子 RMW、锁或系统 API。普通栈/堆计数只经过固定成本的映射范围判断，不遍历槽位；只有映射内的地址才执行最多 64 项的请求检查。测试使用不可读 token 页核实范围外快路径不读取 token。补充接口注释，没有改动函数签名、导出序号或 ABI 版本；既有 Wintun facade 和 Rust 调用使用独立计数。

## 测试与资源核实

`tests/model/batch_output_tests.c` 复用实际 DLL 会话、池、SRW 门、生命周期和所有权计数夹具。对端调度模型使用实际共享 core 和池函数，未替换 DLL 退休算法；它不是运行中的 SYS/NDIS。

每个进程执行 678 个场景和边界检查，包含完整矩阵预热和两轮测量：

- 所有批宽 1–64、输出位于被归还的首/末槽位、输入 token 别名、合法持有的其他 TX/RX 借用输出、下一代重新接收。
- 提交前拒绝危险输出，借用及 Producer 保持不变；换用独立计数可继续提交/归还。
- Reserve/Poll 的计数与输出记录重叠时，内部账本仍由私有计数决定。这里验证无效/破坏性输出布局不会污染内部控制，不保证相互覆盖的公开记录还能同时保留两个值。
- 合成环压力下的部分接受、前缀完成和剩余重试；这是边界注入，不宣称正常布局必然能出现这种占用组合。
- 停止后的满 recycle、本地故障退休；用户借用清零仍不能越过未归零的原生引用。
- 四字节区间的开始/末尾交叉、未转交槽位、映射边界和范围外快速拒绝重叠判断。
- 真正的队列所有者线程在发布/对端重用后暂停；停机线程此时仍看见借用和 DataGate，不能提前准备回收。原生引用在两个不同顺序归零，所有者真实退出并加入后才最终关闭。

逐个会话跟踪并核实应用创建的事件、线程句柄、工作项、私有线程池和保护页分配均归零，线程逐一等待退出后关闭。初步整进程采样出现过句柄差异：回调完成、池已关闭和原生工作线程已经终止不是同一观察点。测试在每个实际回调入口复制当前线程对象作为见证，回调加入并关闭池后等待全部见证真实终止，再关闭见证句柄和采样；不依赖线程 ID 再查询，避免重用竞态。整进程句柄数先预热完整矩阵，再连续两轮检查不增长，保留原始数值；异步清理也可能使数值下降。没有用放宽持续增长上限替代归属检查。

CPU 审计复用实际 DLL return-cycle 基准，以固定线程亲和性做七轮交替 A/B 测量，保留原始 ns/cycles、样本中位数和编译器原生代码清单。该结果只描述宿主开销，不代表内核 CPU、NDIS 吞吐或时延保证。

```powershell
pwsh -NoProfile -File tools/audit/verify-batch-output.ps1
pwsh -NoProfile -File tools/audit/verify-sys-return-reclaim.ps1

```

审计校验冻结 queue 头文件 SHA-256，以 ISO/MS volatile、普通/保护页内存要求旧代码出现指定 51/52 标记，当前实现通过完整矩阵。日志、源指纹、二进制哈希和 CPU 样本存入 `out/batch-output-audit/<指纹前12位>/evidence.json`。Tests/UnifiedTests 与 Safety 自动执行新增用例。

本轮 SYS、共享 core、公开数据协议、Rust 源码和系统能力门控未修改；继续回归原生回收双屏障、并发归还、暂停/停机唤醒和退休预算。没有因未证实的内核问题改动同步顺序，也未引入旧系统不支持的 API。真实旧/新 Windows、签名安装、NDIS、Driver Verifier、休眠/移除和长期内核泄漏测试仍待实机完成：`kernel_runtime_tested=false`、`production_ready=false`，构建产物为未签名开发产物。
