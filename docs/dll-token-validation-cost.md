产品版本保持 2.0.0，PE 文件版本保持 2.0.0.0。
Data/API 2.1、packet 1.1、lifecycle 1、共享布局和导出函数表均不变。

## 确认的问题

起始源码指纹为 `723356587cb81a541c16bd977ca78ba7a9f9dea971a31acf1dfbb914005634d0`。
修改前的核心和队列头保存在 `out/dll-token-validation-baseline/723356587cb8`。
旧 `common/v2_core.c` 的 SHA-256 为
`1aa57419605064ed1422473b439bd183def99045f112c5d708b20074346794f0`。

`PbPoolImport` 和 `PbValidateTokens` 在每项所有权检查后，都从头回扫前面的
slot，排除同批重复。一个合法、无重复的 32 项批次，在每个函数中都要执行
0 + 1 + … + 31 = 496 次精确 slot 比较。完整 DLL 收取/归还循环同时经过这两处；
取消、提交和完成消费也调用相同的 token 批量校验。

这确认了批处理中的重复 CPU 工作，不是新的槽泄漏或漏唤醒证据。

## 修正和维护依据

两处共用一个私有内联选择函数，1–8 项保留原精确比较；更大的批次使用本次调用
的 64 位局部值记录 slot 的低六位。
同一个 slot 必定映射到同一位：该位不存在时，可以跳过此前 token 的回扫；
该位存在时，仍执行原来的逐 slot 精确比较。例如 0 和 64 共享同一位，但不会
因此被拒绝。筛选命中本身不能授权或拒绝所有权。

筛选仍在当前 token 的 epoch、queue、slot、generation、state，以及导入时的
空闲索引检查之后执行。无效当前 token 的错误继续优先于其重复性；已发现的
重复继续优先于后续 token 的错误。导入第二个循环仍只在整批验证通过后更新
代次、状态和空闲位图，任意失败都不产生部分导入。

单项归还校验直接使用既有单 token 验证；短批次不执行位筛选。没有增加 512 位
逐批清零数组、堆分配、池缓存、共享字段、锁或原子操作。局部值每次从零开始，
不会跨会话、队列、epoch、调用或故障留存。两处共享筛选规则，实际所有权规则
继续由原函数负责。

筛选不保证最坏情况为线性时间。同位冲突集中时仍可能执行原有的二次回扫，
精确比较次数不超过原实现，另有至多 32 次局部筛选成本。保留这个有界回退，
可以在较小生产变更下保持全部返回码和原有错误顺序。

## 所有权、内核回收和唤醒核对

| 路径 | 本轮保留的依据 |
| --- | --- |
| DLL 收取 | 描述符先验证，再整批导入镜像池；失败不发布部分 loan |
| DLL 归还/取消/提交/完成 | 整批 token 先验证；只有实际接受或完成的前缀推进既有状态与计数 |
| DLL 故障归还 | 仍须合法 owner 和 token；本地 loan 退休不替代真实 native close 屏障 |
| SYS TX 回收 | TxLock 下逐项验证 token，四批/128 项预算和有效前缀后的故障停止规则不变 |
| RX 归还和完成背压 | Active、credit、pending 仍由实际归还和完成发布推进，不能由局部筛选值授权释放 |
| worker/DLL 等待 | Armed、producer/consumer 发布顺序、空间通知、暂停回收和有限 DRAIN 均不变 |
| 最终回收 | Device Close、worker join、AllReturned、Returns rundown 仍保留 |

SYS 当前回收路径不调用这两个批量函数；本轮未改写其等待或回收协议。共享核心
仍同时经过 SYS/DLL 构建和完整回归，并要求两者来自同一源码指纹。

## 独立模型、原生代码和 A/B

`token_validation_tests.c` 的参考模型使用逐 slot 布尔集合，独立于生产筛选法。
每个变体执行 578,816 个矩阵用例和 32,736 个重复位置/错误顺序用例，覆盖：

- 1 至 32 项批次、17 个池容量边界、连续/逆序/跨 64 槽/混合分布和全部槽状态。
- 每个错误位置的 scope、零/旧/最大代次、状态与空闲位图错误，以及同位不同槽。
- 所有重复位置对、重复项自身先遇 stale、较早重复先于后续 stale 的错误顺序。
- 池、槽数组和输入后的保护页，单项读取范围、首错短路、输入不变、逐字节池状态、
  代次、Next 和空闲索引一致；错误批次不得部分提交。

`verify-dll-token-validation.ps1` 校验旧文件哈希，在 ISO/MS volatile 模式分别
执行冻结/当前实际核心、实际 API/lifecycle 回归及独立模型。操作计数只插在真实
精确比较和筛选处：连续 32 项的每函数比较从 496 降为 0，筛选 32 次；8 项同位
不同槽仍比较 28 次，筛选计数为 0。32 项跨四组同位槽比较 448 次，保留精确回退。

计时使用未插桩的实际核心和 DLL，固定允许 CPU，七轮交替测量六种批量长度，
保留所有样本、源码/二进制哈希和原生代码列表。短批次分流后的 A/B 证据位于
`out/dll-token-validation/cd95d89bb3f2/evidence.json`，宿主 DLL 收取/归还循环中位数为：

| 槽位分布/批次 | 原实现 ns | 当前 ns |
| --- | ---: | ---: |
| 连续，1 项 | 94.34 | 95.26 |
| 连续，8 项 | 176.49 | 178.39 |
| 连续，32 项 | 682.58 | 449.94 |
| 跨 64 槽，8 项，集中冲突 | 173.83 | 174.99 |
| 跨 64 槽，32 项 | 680.31 | 618.45 |

收益依赖批次和槽位分布。初次对照中集中冲突的 8 项批次出现数 ns 的筛选成本，
因此最终限定 1–8 项沿用原精确扫描。短批次仍有分流判断和测量波动，不将小幅
变化作一致加速结论，也不能把连续 32 项约 34% 的宿主收益推广到所有流量。
普通发布和 pending 环的控制基准也完整
保留。上述循环没有实际驱动 I/O、NDIS 调度或业务 payload 工作，不代表内核 CPU、
端到端延迟或吞吐结果。
