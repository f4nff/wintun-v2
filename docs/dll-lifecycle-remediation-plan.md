# DLL 生命周期与并发修正方案

日期：2026-10-29。状态：阶段 A 至 E 及阶段 F 的代码与宿主验证已实施，真实驱动和性能验收待执行。实现、版本迁移和验证入口见 [实施记录](dll-lifecycle-implementation.md)。范围为 PacketBridgeV2 DLL、配套 SYS 生命周期接口及 Rust 绑定；旧版 Wintun DLL 的回调卸载修正单独验证。

采用统一的资源所有权和退出状态机，拆开数据访问、控制请求串行化、对象存活保护。关闭超时限制调用者等待，后台资源继续由明确的所有者负责。性能改动在退出协议稳定后实施。

本方案不修改实际 Rust VPN 应用，不安装或加载驱动。后续应用接入、组件版本更新和签名包重建分别安排。

## 1 已确认的问题与修正目标

| 问题 | 当前根因 | 修正后的行为 |
| --- | --- | --- |
| V2 空闲等待挡住策略变更，随后 Wake 也被挡住 | 一把 Control SRW 锁同时保护对象存活、数据访问和控制请求；Wait 持共享锁睡眠 | Wait 睡眠只持对象引用；策略串行化与数据等待互不依赖；Wake 不等待控制写锁 |
| Close 与 PrepareClose 的 timeout 不覆盖阻塞清理 | 同步 Drain IOCTL 位于计时之前，最终 CloseHandle 和 SwDeviceClose 也在调用线程执行 | 调用线程发布关闭请求并等待本地进度事件；阻塞清理由受生命周期保护的执行通道负责 |
| 旧版清理回调可能跨越 DLL 卸载 | QueueUserWorkItem 没有模块引用、任务句柄和可观察的退出协议 | 提交之前持有模块引用；任务退出和回调返回都有对应的释放步骤 |
| Rust 隔离列表可能永久增长并阻塞其他回收 | Drop 执行同步 Close，reap 在全局 Mutex 内执行外部调用 | Drop 移交所有权；回收不持全局锁调用驱动；隔离有资源预算、原因和进度 |
| Wait 和关闭路径产生重复查询 | 每次 Wait 查询驱动；关闭阶段固定 Sleep(1)、全量扫描和查询 | 热路径读取终止通知；清理由专用进度通知推进；显式诊断查询保留 |

## 2 必须维持的所有权规则

1. 公开 session 句柄、后台执行任务、正在执行的 API 各自持有明确的存活引用。引用只能延长一个已经合法取得的对象的寿命，不能使任意旧指针安全；C 调用者仍须在最终销毁前停止并 join 所有使用者。
2. packet lease 是独立于 API 调用的长期借用。API 已返回不代表其 Data 指针已失效。存在接收 lease 或未取消的 reserve 时，禁止释放对应映射。
3. CloseHandle 所触发的驱动退出屏障完成之前，映射、事件和适配器引用继续存在。共享状态页、超时、取消请求成功、ActiveReferences 的一次快照都不能单独授权释放。
4. 后台任务持有自己的 DLL 模块引用；Rust Arc 负责公开对象的库引用。两个所有者分别释放各自的引用，任何一方都不能替另一方提前卸载 DLL。
5. 资源最终回收只有一个执行者。Close 重试、PrepareClose、Drop、设备移除和显式 shutdown 汇入同一实现，不能分别复制析构流程。
6. 对象仍可能被内核或回调访问时，隔离保留资源；通过准入预算限制后续增长。超过预算时拒绝新会话或新适配器，不释放仍在使用的旧资源。

建议在 `api/v2` 中按职责拆出 lifecycle、control、queue、status 四个内部模块，`session.c` 保留接口适配和组合。只有资源所有者及其析构代码使用最终释放函数。内部类型不暴露给 ABI。

| 所有者 | 所拥有的资源 | 交付或释放条件 |
| --- | --- | --- |
| session 公开句柄 | 一份 session core 引用 | Close 成功，或显式 ReleaseSession 移交后失效 |
| session core | Device、映射、队列事件、slot 元数据、Adapter 引用 | 所有用户 lease 归还，数据访问静止，驱动退出屏障完成 |
| 控制执行通道 | 预创建工作对象、执行引用、模块引用、请求与完成事件 | 停止接收请求，最后一次执行退出；模块引用覆盖回调返回尾部 |
| adapter | 软件设备句柄、路径、元数据 | 调用者及 session 引用全部释放，软件设备关闭屏障完成 |
| 旧版清理任务 | 回调上下文、调度状态、模块引用 | 取消或完成清理，回调返回后释放最后的模块引用 |

## 3 状态机与锁的职责

生命周期采用单向阶段：`Running -> StopRequested -> Draining -> Prepared -> Releasing -> Closed`。故障原因与 `Quarantined` 作为附加状态记录，避免每次超时重新发起排空、延长原有排空期限，或把未知状态错误转回 Running。此阶段枚举与驱动现有 PB_SESSION 状态分别定义。

`StopRequested` 立即停止新 reserve、commit 和新 packet 借用，并唤醒全部等待者。已借出的缓冲区继续允许 Release/Cancel，完成项继续可以推进。`Prepared` 表示已达到排空条件，公开句柄仍可查询；它不消费公开句柄。`Releasing` 执行实际关闭屏障，`Closed` 表示资源释放已完成。

将当前 Control 的职责拆成以下三类：

| 机制 | 保护内容 | 不允许跨越的操作 |
| --- | --- | --- |
| 存活引用与入口门 | 已合法进入的调用、后台任务和资源所有者 | 不承担策略排序，也不等同于 lease 计数 |
| 短 DataGate | ring 私有 cursor、pool 状态、lease 计数及清理接管 | Wait、DeviceIoControl、CloseHandle、SwDeviceClose、用户回调 |
| 控制请求队列与短状态锁 | 策略顺序、幂等关闭请求、任务调度及结果发布 | 阻塞 I/O、等待线程和等待 NDIS |

状态锁与 DataGate 尽量不嵌套。清理先在短临界区取得快照或标记执行权，释放锁后执行外部调用，再发布结果。锁顺序和允许调用的函数写在内部头文件，并加调试断言。

Wait 的流程固定为：取得存活引用和队列 owner 资格；在短 DataGate 内检查状态并 arm ring；释放 DataGate；等待数据事件或永久终止事件；观察终止状态并释放引用。保留 arm 后复查，覆盖通知与入睡交错，不能用简单 ResetEvent 加 Wait 替代。

Wake 只取得存活引用并 SetEvent，不进入策略排序路径。策略请求在自己的执行通道中串行化，Wait 是否空闲不影响其获得执行权。清理处理 ring 时必须通过 DataGate 或完成明确的 owner 接管，不能与队列 owner 并发消费同一个 ring。

## 4 关闭执行与超时语义

每个 session 预创建一个控制工作对象及关闭上下文，最多存在一个排队或运行的执行实例。分配失败在 Open 的取得与失败清理链中处理，Drop 不再临时创建线程或分配关闭节点。

执行通道采用每会话私有单线程池和一个 work object，隔离不同会话的阻塞清理。每个加载的 DLL 运行时统一限制会话、适配器和映射预算；多 DLL 实例的进程另由应用统一控制总量。长期阻塞不占用调用者的默认线程池，也不为每次 Close 重试创建任务。运行期未使用的执行线程由线程池管理。

同一个 work object 的多次 Submit 可以产生并行回调，不能依赖 Windows 自动串行化。用短状态锁维护唯一 scheduled/running 状态和请求序号；执行者退出前复查待处理序号，覆盖“最后一次检查与新请求提交”之间的丢失唤醒。关闭只记录一个幂等意图，拥有独立的预留位置，不能因策略请求队列已满而提交失败。策略请求数量有界，不静默覆盖仍需确认的中间请求。[SubmitThreadpoolWork 契约](https://learn.microsoft.com/en-us/windows/win32/api/threadpoolapiset/nf-threadpoolapiset-submitthreadpoolwork)

请求参数和 I/O 输出缓冲由执行通道拥有，调用者超时或取消等待后仍然有效。每个确认对应请求序号；晚到的策略确认不能覆盖已经发布的停止状态。回调不能等待自己的 work object，线程池及其工作对象也必须有明确的关闭所有者。最终模块引用的释放延迟到回调返回之后。

Close 与 PrepareClose 从入口建立单调时钟 deadline，执行发布请求和等待进度两件事。`timeout=0` 只请求并检查已有结果，不在调用线程执行 Drain、查询或最终析构。所有后续等待使用同一 deadline 的剩余预算。调度延迟仍受操作系统影响，接口不承诺硬实时。

| 调用或结果 | 语义 |
| --- | --- |
| PrepareClose 返回 PB_BUSY | 用户仍持有 lease；会话已经停止接纳，句柄保持有效，调用者应归还 lease |
| PrepareClose 返回 PB_OK | 已排空，可以在使用者停止后最终关闭；句柄保持有效 |
| Close 返回 PB_QUARANTINED | 调用者预算已用完，后台仍拥有资源；原句柄继续可查询和重试 |
| Close 返回 PB_OK | 所需关闭屏障和资源释放完成，公开句柄被消费 |
| ReleaseSession | 新扩展接口，消费公开句柄并把剩余清理责任交给原生运行时；之后不得再用该句柄 |

执行者在确认用户 lease 已归还、数据调用静止后进入最终释放；按照 Device 关闭屏障、队列与映射、Adapter 释放的顺序推进，并分别记录当前阻塞阶段。通知调用者完成后仍可能执行的回调尾部继续由执行引用和模块引用保护。

实际阻塞的同步 IOCTL、CloseHandle 或 SwDeviceClose 可以让该会话长期停留在隔离状态。明确区分“调用者已按预算返回”和“资源已安全回收”；不得通过 TerminateThread 或超时 VirtualFree 伪造后者。仅改成 OVERLAPPED 加 CancelIoEx 也不能证明退出，取消请求之后仍须等待 I/O 的最终完成。[CancelIoEx 契约](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex)

在 DLL 内改变调用执行位置即可修复调用者的超时边界，第一轮不重写内核 indication 与 rundown 屏障。后续 SYS 改动集中在进度发布；如果另行将内核控制请求改成可取消 pending IRP，必须作为独立驱动设计验证取消、Halt 与唯一完成的竞态。

## 5 ABI 与 Rust 的迁移

保持现有 PbGetInterfaceV2 的 280 字节布局、函数偏移和结果枚举。旧入口适配同一生命周期核心；Drain 和 SetPolicy 没有 timeout 参数，仍可等待操作确认，但不再与数据 Wait 共用锁。它们的同步语义不能冒充有界停止接口。

新增单独协商版本的生命周期扩展表，提供 BeginStop、BeginSetPolicy、操作进度查询与有界等待、GetCloseProgress、ReleaseSession。表头携带 Size、Major、Minor 和能力位，按已定义前缀读写；测试不同大小和版本，避免再次依赖全表大小永久相等。函数表 ABI 与共享数据 ABI 分别命名和协商。

新 Rust 绑定要求生命周期扩展；旧 DLL 配对旧绑定。原始 V2 C 接口继续可用，但新 Rust 绑定不静默降级为仍可能阻塞 Drop 的旧路径。发布时明确组件兼容矩阵和加载错误。

Rust 的 request_stop 使用 BeginStop，策略控制使用带请求序号的提交与有界等待，Drop 使用预备好的 ReleaseSession 移交路径。显式 close 继续返回实际清理结果，保留 Session/Queue/lease 的借用限制。公开句柄与后台 core 分离，保证 PrepareClose 返回后仍能查询，Close 超时后也不会留下悬空句柄。

BeginStop 成功只确认本地停止接纳和请求已提交；禁用 offload、排空完成和允许替换组件分别等待对应的原生确认。Rust fallback 控制器必须依据请求序号和确认阶段前进，不能把一次成功提交当成策略已经应用。既有 Open、CreateAdapter 及诊断查询仍明确属于同步接口；若应用需要它们也能取消等待，后续通过同一执行协议提供独立的异步创建接口，不把借用栈指针直接传给后台任务。

取消当前 Rust 全局 Vec 作为资源最终所有者的职责，由原生运行时负责继续推进和统一记录隔离。迁移期间若保留旧 reap 接口，先从 Mutex 内取出一批工作，解锁后再执行原生调用，再合并未完成结果；不持全局锁跨越驱动调用。重复回收同一 session 必须有唯一执行权。

诊断快照至少包括 session 标识、状态、阻塞阶段、原始错误、用户 lease 数、已知内核引用、保留字节、隔离开始时间、最近进度时间和重试次数。永久设备移除后取不到状态的对象单独记录“无法确认安全回收”，不把 IOCTL 失败推断为内核引用已经归零。

## 6 旧版 DLL 回调与卸载

旧版采用独立小范围提交，保留现有 Wintun 公共函数行为，不引入 V2 数据 ABI：

1. 用具备回调实例的线程池任务替代裸 QueueUserWorkItem。提交前取得真实模块引用并建立任务上下文，引用覆盖尚未开始执行的排队区间。
2. 回调通过 FreeLibraryWhenCallbackReturns 安排尾部释放，避免在最后几条 DLL 指令执行前释放最后的模块引用。入队失败必须回滚 working 标记、任务计数、上下文和模块引用。回调完成与新清理请求的交错纳入调度状态机。[回调返回后的模块释放](https://learn.microsoft.com/en-us/windows/win32/api/threadpoolapiset/nf-threadpoolapiset-freelibrarywhencallbackreturns)
3. 合并重复清理请求；安装互斥锁等待可响应 shutdown，并按批次检查取消。SetupAPI 内部仍可能阻塞，相关任务在返回前继续持有其资源和模块引用。
4. 在普通导出调用中完成按需初始化，把设备枚举、遗留设备清理和可触发延迟加载的初始化移出 DllMain。DllMain 不 join 工作、不等待清理事件，也不通过抢用户锁完成 shutdown。[DLL 初始化约束](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices)
5. 提供普通调用上下文中的显式 shutdown：停止接纳任务、请求取消、等待已运行任务和相关 logger 回调退出。未调用 shutdown 的旧客户端仍由任务模块引用保证卸载安全；不得让新 API 成为修复旧竞态的唯一前提。

V2 的 SwDeviceCreate 回调继续保留现有关闭屏障。若将创建过程也改成提前返回的异步接口，必须把栈上的创建上下文迁到拥有引用的对象；在 SwDeviceClose 屏障完成前保留事件和上下文。[SwDeviceClose 契约](https://learn.microsoft.com/en-us/windows/win32/api/swdevice/nf-swdevice-swdeviceclose)

## 7 进度通知与 CPU 改动

CPU 改动在生命周期回归通过后单独提交，使性能差异和正确性变化可以分别回退。

第一步，在共享区域增加由内核发布、用户态读取的终止状态和进度序号，并注册独立的生命周期通知事件。使用新的共享 ABI minor 和能力位协商，SYS、DLL、probe、Rust 同步更新；字段不挤入未声明的 padding。控制状态的发布使用明确的 release/acquire 语义，内核的资源判断继续来自私有状态。组件版本、源码指纹、打包清单和应用绑定同步更新，旧包不混用。

Wait 根据 ring、永久关闭事件和终止状态决定返回，不再每次执行 QUERY。显式 GetStatus 仍可取得完整状态。读取终止状态只授权停止工作，不授权释放映射；最终释放始终经过实际关闭屏障。

清理执行者监听专用进度事件，不消费队列 owner 的自动复位 UserEvent。completion 推进、最后引用归还、排空与关闭确认更新进度；采用序号加 arm 后复查防止通知合并导致丢失唤醒。只在有进度或低频诊断到期时复查，移除固定 Sleep(1) 循环。完成处理保留单轮描述符预算。

第二步，在合法 token 状态转换处按批次维护用户 lease 和已发布缓冲计数，减少关闭阶段反复全量扫描。调试构建保留受保护的全量扫描交叉核对；错误或计数不一致进入隔离，不能据计数直接提前释放。

最多 32 项的重复 token 检查和最多 512 slot 的池扫描继续保留，除非采样证明值得改动。若后续用位图或空闲链替换，必须验证 generation 退役、乱序完成和重复归还。内存屏障、范围检查和 token 所有权不能作为降低 CPU 的删减项。

## 8 实施顺序与验收

| 阶段 | 主要改动 | 进入下一阶段的条件 |
| --- | --- | --- |
| A 固定契约和测试基线 | 将审查复现迁入 tests；明确单包 written 失败清零、批量输出保留成功前缀；修正对应断言；形成状态与所有权说明 | 当前完整 Tests/Safety 构建可运行到底；新用例在旧实现上稳定复现问题 |
| B 修复旧版卸载 | 模块引用、可观察任务、入队失败回滚、普通上下文 shutdown、DllMain 按需初始化 | 子进程反复加载、关闭、卸载；提交失败与回调挂起场景无提前卸载和资源重放 |
| C 拆分 V2 同步职责 | 存活引用、短 DataGate、独立策略串行化；Wait 在锁外睡眠，Wake 独立 | 空闲 Wait 下策略可完成；策略排队时 Wake 可完成；跨队列故障和 Wait 取消不回归 |
| D 建立关闭执行通道 | 预创建 work object、有界调度、进度快照、入口 deadline、独占最终析构 | Drain/CloseHandle/SwDeviceClose 分别挂起时 Close(0) 可返回；解除阻塞后按顺序只释放一次 |
| E 迁移 ABI 扩展和 Rust | 生命周期扩展表、所有权移交、非阻塞停止与 Drop、隔离预算 | 版本矩阵、FFI、借用编译失败、Drop 无新分配、隔离额度与跨会话进度测试通过 |
| F 优化 CPU 并做系统验证 | 独立进度通知、终止状态发布、计数替代扫描、性能采样 | 无丢失唤醒和提前回收；实际系统的资源与性能指标达到验收要求 |

阶段 C 是完整结构修正的第一步，不作为全部退出问题已经解决的发布结论。各阶段使用同一核心实现，不保留两套并行关闭逻辑；控制执行通道、ABI 扩展和进度通知分别形成可审查的提交。

回归测试优先使用可控事件构造顺序，以内部进入点和完成点建立 happens-before。超时只作 watchdog，不依赖线程恰好 Sleep 到某个时间来证明竞态。调用公共入口，mock 外部 Windows/NDIS 边界，减少直接包含整个 session.c 才能观察内部状态的测试耦合。

| 验证对象 | 必须覆盖的场景 |
| --- | --- |
| 同步与唤醒 | Wait 的 arm 前、arm 后、入睡前后收到数据或停止；策略排队；多队列；重复终止；关闭与新入口交错 |
| 资源与超时 | 每个新增取得点失败；持有 lease；晚到 completion；重复 Close；PrepareClose 后查询；公开句柄移交；后台回调尾部 |
| 阻塞隔离 | 每个阻塞屏障单独挂起；一个会话挂起时其他已接纳会话可推进；达到预算后拒绝新资源；解除阻塞后回收 |
| 回调与卸载 | 回调未开始、执行中、最后一次访问之后卸载；调度失败；shutdown 与重复请求；最后模块引用释放；进程退出 |
| ABI 与错误 | V2 原布局；扩展表前缀；错误版本；缺失能力；设备移除导致永久 IOCTL 失败；原始错误可诊断；请求超时后缓冲仍有效 |
| Rust | request_stop、策略确认、显式 close 和 Drop；Queue 非 Send/Sync；lease 阻止最终销毁；移交后不再调用原句柄；晚到确认不撤销停止 |

挂起和 DLL 卸载测试在受控子进程运行，子进程负责自己的测试资源；清理 watchdog 可以结束测试进程，不在产品中终止仍持资源的线程。宿主跟踪应同时检查对象引用、句柄、映射、模块引用和任务数。解除人为阻塞后回到预热基线；真实无法回收的隔离对象则验证记录完整和预算有效。

实际驱动验收覆盖 pause/restart/Halt、适配器禁用和移除、低资源、进程退出及过滤驱动组合，并使用 Driver Verifier、PoolMon 和 ETW/WPA。性能对比至少记录空闲与繁忙时的 IOCTL 次数、唤醒次数、线程 CPU 时间、CPU/GB、吞吐、关闭延迟分布和最坏资源保留量，按相同队列数、slot、包长和卸载配置比较。可直接检查的门槛是：普通 Wait 不再发 QUERY、空闲关闭不固定频率轮询、Close 调用线程不执行阻塞析构。吞吐与 CPU/GB 的发布预算在实测基线后固定，性能回退不得超过预先确定的预算。

静态分析保留原始诊断，对已确认的所有权移交或前置条件记录理由，不以批量 suppress 替代修正。构建测试摘要改为从真实测试结果提取数量与状态，防止新增用例后仍输出旧的硬编码通过计数。

最终交付应包括状态机与锁约定、单一生命周期实现、C/Rust 兼容矩阵、正式回归、低资源和真实系统结果，以及隔离资源的诊断与部署预算。已有审查记录继续作为历史证据，本方案与后续实施结果分别维护。
